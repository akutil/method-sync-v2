## R2-01 [confirmed, major, correctness] The runs/ containment check follows the final fixture.json symlink, but the write doesn't. A symlinked runs/<slug> plus a link back into runs/ passes the check and the fixture is written outside runs/

- **Місце:** `src/method_sync/live.py:277`
- **Доказ:** `_require_inside` checks `target = fixture.resolve()` (line 277) with `if root not in target.parents` (line 280), so it follows the last path component. `_write_atomically` does not: it creates `.fixture.json.<hex>.tmp` in the unresolved `directory`, then `os.replace`s that directory entry without following it. The check and the write therefore look at different paths. Probe on Python 3.14 against a local 200 server: `runs/fapi-v1-premiumIndex -> docs/` plus `docs/fixture.json -> runs/decoy.json`. `capture()` returned `runs/fapi-v1-premiumIndex/fixture.json` with no error, and `docs/fixture.json` became a regular file holding the fixture (the temp file is created in docs/ too). This is the FR-91 scenario (`runs/<slug>` -> `docs/`) with one extra link, for example a hypothetical 'latest fixture' link in docs/ that points into runs/. It also contradicts the docstring's claim that a symlinked `runs/<slug>` always gives FixtureWriteError. v1's `assert_writable` resolved the full path because v1 wrote through the link with `write_text`. That no longer matches a rename-based write.
- **Пропозиція:** Check the directory the write happens in: `where = fixture.parent.resolve()`, require `where.is_relative_to(root)` (this still allows slug '' and '.' as today), and name `where / fixture.name` in FixtureWriteError. `os.replace` never follows the final entry, so `fixture.json` itself needs no resolving. I monkeypatched this version in and it passed the relevant existing Fixture/Slug tests (5 green). It refused the probe case and named docs/fixture.json, which is what the FR-91 scenario expects. Add a regression test for the symlink pair.

## R2-02 [confirmed, major, correctness] A deeply nested body that fetch() accepts makes json.dumps in capture() raise a raw RecursionError, an exception outside the three allowed types

- **Місце:** `src/method_sync/live.py:219`
- **Доказ:** The R1-01/R1-10 fix only converts `UnicodeEncodeError` from serialization into a typed error. The `json.dumps(..., indent=2, allow_nan=False, default=str)` call at lines 219-220 has no guard. On 3.14 the encoder uses more C stack per nesting level than the decoder in `fetch`, and `fetch` does catch RecursionError. Probe through `capture()` with a local 200 server and body `{"a":` + `[`*(d-1) + `1` + `]`*(d-1) + `}`: d=20000 wrote a fixture; d=25000 to 27737 (about 55 KB) raised a raw `RecursionError: Stack overflow (used 3906 kB) while encoding a JSON object`; d>=27800 became a LiveUnavailable from loads. Nothing is written and the old fixture survives. Still, a hostile or broken endpoint can make the CLI print a traceback, which design Goals, D11 and NFR-11 rule out.
- **Пропозиція:** Wrap `json.dumps` in `except (RecursionError, ValueError)` and raise `LiveUnavailable(build_url(base_url, path, args), 'тіло надто глибоко вкладене, щоб записати фікстуру: …')`. Alternatively, move a depth or serializability check into `fetch` so `fetch` and `capture` agree on what counts as available. Add a regression test with a body about 26000 levels deep. A related, lower-impact case (probed): `args = { limit = 0x<4000 hex digits> }` passes `registry.load()`, because the 4300-digit limit does not apply to base 16. `build_url`'s `urlencode` then raises a raw ValueError out of capture(). The R1-05 fix only covers integers rejected at parse time.

## R2-04 [confirmed, minor, security] Proxy CONNECT failure text bypasses _server_text: raw ESC/BEL/C1 and 60 KB reach the LiveUnavailable reason (R1-09 fix incomplete)

- **Місце:** `src/method_sync/live.py:422`
- **Доказ:** urllib's default ProxyHandler (still in build_opener) honours https_proxy and, on macOS, the system proxy. For a non-200 CONNECT answer, http.client._tunnel raises a plain OSError(f"Tunnel connection failed: {code} {message}"), and do_open wraps it in URLError. _client_reason sanitises only HTTPException (line 422), so this text goes out raw. Attacker: a hostile proxy, or anyone on the plaintext client→proxy leg; this works even with an https:// base_url, because CONNECT happens before TLS. Probe (fake proxy on 127.0.0.1, https_proxy set, live.fetch("https://fapi.binance.invalid", …)): the reason was 60,049 characters and carried raw 0x1b, 0x07 and 0x9b ('Tunnel connection failed: 403 \x1b]0;PWNED\x07\x1b[2J\x9b31m …'), which add-run-cli would print to the terminal as is (D11). Probe script: /private/tmp/claude-501/-Users-akutil-humex/9f0df3ff-0f78-42b4-8deb-b5e7dd6a7b4b/scratchpad/r2sec/probe_proxy.py (mode hostile).
- **Пропозиція:** Send every client reason through _server_text, not only HTTPException, e.g. `return _server_text(str(cause)) or type(cause).__name__`. Fixed OS, SSL and gaierror messages come out unchanged, and the existing strerror assertions still hold. Add a regression test with a fake CONNECT proxy that answers 403 with a hostile reason phrase, and assert the reason with assertServerTextSafe.

## R2-05 [confirmed, minor, security] The verdict cut does not reach the proxy CONNECT exchange: a proxy that drips its answer keeps the worker thread and socket alive after the verdict (R1-03/R1-08/R1-14 fix incomplete)

- **Місце:** `src/method_sync/live.py:154`
- **Доказ:** _Connection.connect hands the socket to _Line only after super().connect() returns. Inside that call, HTTPConnection.connect runs _tunnel(), which sends CONNECT and reads the proxy's status line and headers. So with https_proxy set or a macOS system proxy, a proxy (or a MITM on the plaintext proxy leg) that sends its CONNECT answer one byte at a time, each within the socket timeout, holds the thread exactly as in R1-08. The new D8 claim that the socket is registered 'одразу після TCP-з'єднання, ще до рукостискання TLS' does not hold for proxied connections, and D8's 'Ціна' paragraph does not mention the tunnel. Probe (fake proxy sends one header byte every 0.05 s, timeout=0.3): verdict at 0.306 s, the 'method-sync live call' thread was still alive at +0.5, +1.5 and +3.0 s, and the proxy kept sending until the process exited (BrokenPipeError after 3.37 s). Probe script: /private/tmp/claude-501/-Users-akutil-humex/9f0df3ff-0f78-42b4-8deb-b5e7dd6a7b4b/scratchpad/r2sec/probe_proxy.py (mode drip).
- **Пропозиція:** Register the socket before the tunnel. For example, override _tunnel in _Connection to call line.attach(self.sock) before super()._tunnel(); attach already closes a previous duplicate. Or, in __init__, wrap the instance's _create_connection so the socket is attached right after the TCP connect. Update D8 ('Ціна') to match, and add a fake-proxy drip test alongside test_worker_and_connection_end_soon_after_the_verdict.

## R2-06 [confirmed, minor, security] One response header makes capture() raise an untyped MemoryError or OverflowError within 20 ms (R1-08 residual that 6.3 did not cover)

- **Місце:** `src/method_sync/live.py:367`
- **Доказ:** _open_and_read still calls the unbounded response.read(). On 3.14.0, http.client passes the server's Content-Length (or chunk size) straight to BufferedReader.read(amt), which tries to allocate that many bytes up front. The worker stores the exception, and _within_limit re-raises it untyped at line 356, because MemoryError and OverflowError are not in CLIENT_ERRORS. That breaks the design Goal that no input defect leaves the module as a fourth exception class (the CLI would print a traceback). R1-08's evidence already named this 'raise error' path. Anyone serving base_url (or a MITM on http://) can trigger it with a single header and no bandwidth. Probe through live.capture(): 'Content-Length: 2**50' gave MemoryError after 0.018 s, '2**63-1' gave OverflowError after 0.008 s, and chunk size 'ffffffffffffffff' gave OverflowError. The same unbounded read lets a fast body grow memory for the whole 15 s. Probe script: /private/tmp/claude-501/-Users-akutil-humex/9f0df3ff-0f78-42b4-8deb-b5e7dd6a7b4b/scratchpad/r2sec/probe_length.py.
- **Пропозиція:** Read with a cap, e.g. response.read(MAX_BODY + 1) with MAX_BODY around 32 MB, and treat more than MAX_BODY as LiveUnavailable('тіло більше за …'). A probe (probe_cap.py) showed that a bounded read returns 0 bytes, or raises a typed IncompleteRead, for all three headers. Add a regression test with a huge Content-Length and a huge chunk size that expects LiveUnavailable.

## R2-07 [confirmed, minor, security] design.md D9 contains a raw U+202E RIGHT-TO-LEFT OVERRIDE where the escaped example `‮` was intended (hidden bidi control character)

- **Місце:** `openspec/changes/add-input/design.md:143`
- **Доказ:** Line 143 is meant to show that U+202E becomes the escape `‮`. Between the backticks, though, it holds the raw character: a byte scan of all changed files found 0x202E RIGHT-TO-LEFT OVERRIDE on this line only, with no closing PDF (U+202C). Without the PDF, the override reverses how the rest of the line looks in bidi-aware terminals, editors and diff viewers. In rendered Markdown it reverses the rest of the paragraph, because soft-wrapped lines form one paragraph. So the sanitisation text a reviewer reads differs from its bytes. This is the Trojan Source class (CVE-2021-42574) that GitHub flags as hidden bidirectional Unicode text, and this change introduced it into the spec that will be archived.
- **Пропозиція:** Replace the raw character with the literal six-character text ‮. Consider adding a lint check that fails on Unicode Cf/bidi control characters in src/, tests/ and openspec/.

At the real 15 s limit, a compromised endpoint, or a man-in-the-middle on an http:// base_url with a fast link, can push tens of GB into memory. Add a local-server test streaming past the cap. If the orchestrator accepts the risk instead, write it into design D8 'Ціна' and Risks so the three-class goal is not silently broken.

## R2-10 [confirmed, minor, visual] [security] Fixture containment check validates the symlink-resolved final path, but the atomic write lands in the physical parent dir: runs/<slug> -> outside dir plus a back-symlink writes outside runs/

- **Місце:** `src/method_sync/live.py:277`
- **Доказ:** The check and the write were both introduced in this diff, and they look at different paths. `_require_inside` (lines 276-282) resolves the whole `fixture` path with `fixture.resolve()`, so it also follows a symlink in the LAST component `fixture.json`. `_write_atomically` (lines 294-302) never follows the last component: it uses `open(temporary, "xb")` (O_EXCL) and `os.replace(temporary, fixture)`, which replace the directory entry itself (the docstring says so). The real write location is therefore `realpath(runs/<slug>)/fixture.json`, not `fixture.resolve()`. The v1 `boundaries.assert_writable` pattern was only consistent with a direct `write_text`, which does follow the final symlink. Probe with a local 200 server and a temp tree `tool/runs`, `docs/`, `tool/runs/inside/`: `runs/fapi-v1-premiumIndex -> docs/` (the FR-91 scenario's symlink), plus `docs/fixture.json -> runs/inside/fixture.json` (dangling, pointing back inside runs/). `fixture.resolve()` gives `runs/inside/fixture.json`, which is under root, so the check passes. `capture(url, "/fapi/v1/premiumIndex", {...}, runs)` then RETURNED NORMALLY with `runs/fapi-v1-premiumIndex/fixture.json`. The temp file was created in `docs/`, and `docs/fixture.json` is now a regular file holding the full fixture JSON; `runs/inside/` stayed empty. This contradicts FR-91 ('Запис поза коренями не виконується'), constitution principle VII, and design.md D10 step 3 ('посилання runs/<slug> ... назовні дають FixtureWriteError ... і нічого не створено'). The CLI would report success while the bytes land outside runs/. It needs two planted symlinks, one of them outside runs/, so the practical risk is low. Note that runs/ is not in .gitignore. The residual gap belongs to fix 6.2 (R1-11/R1-16): the existing tests cover only the single-symlink cases, where the resolved final path happens to be outside.
- **Пропозиція:** Check the directory the write actually happens in: `where = directory.resolve()` and require `where == root or root in where.parents`. The `==` case keeps slug ''/'.' writing to runs/fixture.json, as D10 allows. On failure raise `FixtureWriteError(where / "fixture.json", ...)`. `open(..., "xb")` and `os.replace` never follow the final component, so this is the true write location. Keeping the current full-path check as well is harmless, since it only adds refusals. Add a regression test next to test_fixture_is_never_written_outside_runs_dir: `runs/<slug> -> docs/` and `docs/fixture.json -> runs/inside/fixture.json`. Assert `FixtureWriteError`, that `docs/fixture.json` is still a symlink, and that files_outside(root, runs) is unchanged.
