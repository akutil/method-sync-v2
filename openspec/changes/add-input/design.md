# Design: add-input

## Context

Перепис двох модулів v1 (`/Users/akutil/humex/method-sync/src/method_sync/registry.py`, `live.py`) під базові
специфікації `registry` і `live-capture`. Еталон читаємо, а не копіюємо: де спека v2 вимагає іншого, v2 іде за спекою
(розділ «Що v1 робив інакше»). CLI ще немає, тож модулі віддають результат або типізований виняток, а коди виходу
призначає `add-run-cli`.

## Goals / Non-Goals

**Goals**

- `registry.load()` перевіряє реєстр цілком до першого методу; будь-яка вада дає `RegistryError`, повідомлення якого
  називає поле і місце (FR-1–FR-10, NFR-11).
- `live.capture()` робить рівно один живий GET і пише фікстуру або кидає `LiveUnavailable` з URL і причиною, не
  лишаючи фікстури (FR-23–FR-29, NFR-4).
- Жодна вада входу не виходить із модулів іншим класом винятку, ніж три названі нижче: інакше CLI надрукує traceback.

**Non-Goals**

- CLI, argparse, коди виходу, stderr, рядки stdout і шкала серйозності — `add-run-cli`.
- Об'єднання живих ключів і значень енамів (FR-38) — `add-field-verification`; тут лише «чи є хоч один ключ» (FR-29).
- Future: коротка форма як повний запис (FR-11), дублі (FR-12), неоднозначний метод (FR-13), параметри з документації
  (FR-95–FR-99), `credentials` для підпису (FR-105).

## API модулів

Тести пишуться до коду, тож імена й сигнатури фіксуються тут.

- `registry.py`: `RegistryError(Exception)`; `slug_for(path) -> str`; `@dataclass(frozen=True) Method` — `path`,
  `model`, `client_method: str`, `args: dict = {}` (через `field(default_factory=dict)`), `call: str | None = None`,
  властивість `slug`; `@dataclass(frozen=True) Registry` — `lib: Path`, `verify_cmd: str`, `base_url: str`,
  `status: object`, `credentials: object | None`, `methods: list[Method]`; `load(path) -> Registry`.
- `live.py`: `TIMEOUT_SECONDS = 15`; `RUNS_DIR = Path(__file__).resolve().parents[2] / "runs"`;
  `LiveUnavailable(Exception)` з атрибутами `url` і `reason`, `str()` — `жива відповідь недоступна: <url> — <reason>`;
  `FixtureWriteError(Exception)` з атрибутом `path`; `build_url(base_url, path, args) -> str`;
  `no_redirect_open(url, timeout)` — типовий відкривач;
  `fetch(base_url, path, args, *, open_url=None, timeout=TIMEOUT_SECONDS) -> (200, розібране тіло)`;
  `capture(base_url, path, args, runs_dir=RUNS_DIR, *, open_url=None, timeout=TIMEOUT_SECONDS) -> Path` фікстури.
- Фікстура: `{"path", "args", "captured_at": "2026-09-30T08:15:02.123456+00:00", "http_status": 200, "body"}`.

## Decisions

**D1. Модель — frozen dataclass, як у v1.** Відмінності від v1: `status` і `credentials` приймають будь-яке значення
TOML (FR-3: `5`, `true`), а не лише рядок; `args` — dict у порядку запису з типами `tomllib` (дата лишається `date`);
`call` зберігається дослівно, зокрема `""`; `lib` — `Path` як записано, лише з `expanduser()`, відносний шлях не
резолвиться (FR-6). `slug_for` і `Method.slug` лишаються в `registry.py`, а `live.py` їх імпортує: slug від `Method`
беруть і звіт, і цикл. Альтернатива — dict чи TypedDict. Відкинуто: наступним слайсам потрібні атрибути й
незмінність, а dataclass перевірено у v1.

**D2. Сувора валідація за один прохід у фіксованому порядку.** Перша знайдена вада кидає виняток. Порядок: файл →
розбір TOML → верхній рівень (невідомі поля → типи → обов'язкові й непорожні) → `lib` (існує, має `.git`) → `[live]`
(невідомі → типи → `base_url`) → `method` (тип, непорожній) → кожен запис по черзі (тип елемента → коротка форма →
невідомі → типи → обов'язкові). Тип перевіряється раніше за «бракує», тож на `lib = 5` повідомлення каже «має бути
рядком». Місце називається так, як вимагає спека: `верхнього рівня`, `у секції [live]`,
`у записі методу #N (<path>)`, а без придатного `path` — `у записі методу #N`. Ціна: людина бачить одну ваду за запуск,
як і у v1. Збирати всі вади означало б складніші повідомлення й тести, а вимоги такої немає.

**D3. Одне правило хибного типу TOML.** Очікувані типи зведено в три таблиці: верхній рівень
`{lib: str, verify_cmd: str, live: dict, method: list}`, `[live]` — `{base_url: str}`, запис —
`{path, model, client_method, call: str; args: dict}`; елемент `method` — `dict` або `str`. Повідомлення називає поле,
місце, очікуваний і фактичний тип словами (`рядок`, `таблиця`, `масив`, `ціле число`…). FR-9 — окремий випадок цього
правила. Не перевіряються `status`, `credentials` і значення всередині `args` (FR-3; спека: «інших перевірок типу
немає»). v1 перевіряв лише `args` і елемент `method`.

**D4. Коротка форма (FR-10).** Рядок як елемент `method` одразу дає `RegistryError` із цим шляхом, словами `model`,
`client_method` і «працювати нема з чим». v1 перетворював рядок на `{"path": …}` і падав на першому відсутньому полі.

**D5. Назовні `load()` виходить лише `RegistryError`.** `OSError` (файлу немає, це каталог, немає прав),
`TOMLDecodeError`, `UnicodeDecodeError` (файл не в UTF-8) і `RuntimeError` з `expanduser` (`~` неіснуючого
користувача) стають `RegistryError` зі шляхом і текстом первинної помилки (`raise … from`). Перші два випадки —
сценарії FR-5, решта — вимога NFR-11: будь-який інший клас винятку CLI покаже трасуванням, як у v1.

**D6. Адреса і схема (FR-23).** `build_url` як у v1: `base_url.rstrip("/") + path`, а для непорожніх `args` —
ще `?` + `urllib.parse.urlencode(args)`. Перша дія `fetch` — перевірка
`urllib.parse.urlsplit(url).scheme in {"http", "https"}`; інша схема дає `LiveUnavailable` («схема … не дозволена»).
Шлюз стоїть до будь-якого відкриття, тож `open_url` не кличеться взагалі. `file://` у v1 читав локальний файл
(проба), а FR-92 це забороняє.

**D7. Без перенаправлень.** `no_redirect_open` відкриває через `urllib.request.build_opener(_NoRedirect)`; у
`_NoRedirect(HTTPRedirectHandler)` метод `redirect_request` повертає `None`, і urllib кидає `HTTPError` з кодом 3xx
(проба: 301, рівно один запит; v1 робив і другий). Шов `open_url(url, timeout)` — як у v1: повертає відповідь, яка є
контекстним менеджером і має `.status` та `.read()`. Тести підставляють у шов лише шпигуна, що делегує в
`no_redirect_open` і рахує виклики. Підроблених відповідей біржі немає.

**D8. 15 с на весь виклик (NFR-4).** Запит і читання тіла йдуть у daemon-потоці, а головний потік чекає
`join(timeout)`. Сокет отримує той самий `timeout`, тож завислий потік відпадає сам. `TimeoutError` із потоку і
прострочений `join` дають одну причину — «перевищено ліміт 15 с»; на тихому сервері вони спливають разом (проба:
`TimeoutError` на 2,00 с при ліміті 2 с). Ще дві проби: тіло, яке сервер віддає по кілька байтів, обірвано на 2,01 с
при ліміті 2 с; процес із завислим daemon-потоком завершився за 1,14 с. Відкинуто:

- тайм-аут сокета, як у v1: він діє на одну операцію, тож те саме тіло тяглося 3,2 с при `timeout=2`;
- `ThreadPoolExecutor`: тримає вихід процесу до кінця завислого виклику (проба: 4,10 с замість 1,14 с);
- `SIGALRM`: працює лише в головному потоці й змінює глобальний стан процесу.

Ціна: після вердикту потік може жити до свого тайм-аута; його результат відкидається, і він нічого не пише.

**D9. Класифікація відповіді (FR-26, FR-29).** Перевірки йдуть у такому порядку:

1. Помилка клієнта. Ловляться `OSError` (зокрема `URLError`, `TimeoutError`, `ConnectionError`),
   `http.client.HTTPException` (`InvalidURL`: пробіл у шляху, нечисловий порт) і `ValueError` (`Invalid IPv6 URL`,
   IDNA); усі три гілки підтвердила проба. `HTTPError` обробляється окремо: причина — статус числом і до 200 символів
   тіла, бо там біржа пише пояснення (`Invalid symbol.`).
2. Статус, відмінний від 200: 204 приходить як звичайна відповідь, а не виняток.
3. Порожнє тіло або тіло з самих пробілів.
4. `json.loads` над байтами кидає `ValueError` (`JSONDecodeError` чи `UnicodeDecodeError`) — причина «тіло не
   розбирається як JSON: <текст помилки>».
5. Немає жодного ключа об'єкта. Доступна лише відповідь-об'єкт із ключем або масив, де хоч один елемент — об'єкт із
   ключем.

Об'єднання ключів тут не рахується: це FR-38 у перевірці.

**D10. Фікстура (FR-24, FR-25, FR-28).** Фікстура пишеться лише після повного успіху `fetch`. Тому недоступна
відповідь не лишає власної фікстури, а фікстура попереднього прогону лишається байт у байт: FR-28 виконується за
побудовою. `RUNS_DIR` виводиться з розташування пакета, як `RUNS_DIR` у `__main__` v1, а не з робочого каталогу;
тести передають тимчасовий `runs_dir`. Серіалізація — `json.dumps(…, ensure_ascii=False, indent=2, default=str)`,
тож дата з `args` стає `"2026-09-30"` (проба; v1 падав `TypeError`). `OSError` на `mkdir` чи записі дає
`FixtureWriteError` зі шляхом каталогу чи файлу. Запис прямий, як у v1, без тимчасового файлу й `os.replace`: зірваний
запис може лишити обрізану фікстуру, але метод тоді зупинено, а FR-28 стосується лише недоступної відповіді.

**D11. Повідомлення.** Тексти українською; поля, шляхи й URL — дослівно (NFR-13). Повідомлення самодостатнє: CLI
друкує `str(error)` без трасування, а первинна помилка лишається лише в `__cause__`.

**ADR:** кандидатів немає — усі рішення локальні для двох модулів і випливають зі спеки або з v1.

## Обробка помилок

| Виняток | Коли | Повідомлення містить | CLI (`add-run-cli`) |
|---|---|---|---|
| `RegistryError` | вада реєстру (FR-2, FR-4–FR-10) | поле й місце, шлях файлу чи `lib` | код `2`, прогін стоїть до першого методу |
| `LiveUnavailable` | схема (FR-23), FR-26, FR-29, NFR-4 | `жива відповідь недоступна`, URL, причину | код методу `3`, решта списку йде |
| `FixtureWriteError` | `OSError` на записі фікстури | шлях каталогу чи файлу | код методу `1`, решта списку йде |

Будь-який інший виняток із цих модулів — дефект інструмента, а не вада входу.

## Покриття сценаріїв у цьому слайсі

Модульні тести доводять усе, що видно з результату `load()` чи `capture()` або з їхнього винятку. Частини
сценаріїв, які видно лише на процесі CLI, отримують тести в слайсі-власнику, а e2e-харнес (`tests/e2e/evidence.py`:
`live-unavailable`, `live-scheme`, `mixed-run`) уже перевіряє їх на живій біржі:

- код виходу, stderr, відсутність `Traceback`, сценарій «Без --registry прогін не починається» (FR-1), рядок методу,
  прогін після невдалого методу, незмінні `runs/` і `git status` бібліотеки, агента не кликали (FR-27) — `add-run-cli`;
- сирий запит раннера на ту саму адресу (FR-30) — `add-field-verification`;
- заборона документації в тексті брифу (FR-30) — `add-sync-loop-and-report`.

## Risks / Trade-offs

- **Тривалість тестів.** Сценарії NFR-4 з буквальними 15 с і 10 с додають до `npm run test:run` близько 25 с. Тест із
  коротшим `timeout` довів би механізм, а не число зі спеки.
- **Локальні передумови.** `127.0.0.1:9` мусить відмовляти в з'єднанні, а `fapi.binance.invalid` — не резолвитись.
  Тест перевіряє це першим і, якщо ні, падає з поясненням, а не пропускається (урок `vacuous-pass-not-earned`).
- **Потік після вердикту.** Завислий daemon-потік живе до тайм-аута сокета; тести закривають сервер у `tearDown`.
- **Мінлива відповідь біржі** між фікстурою і сирим запитом раннера лишається, як у v1 (вимоги, 5.4).
- **Архів губить частину спеки** (проба на копії репо, розділ нижче). Доказ відновлення — порожній `git diff cf8cdd9`
  по обох спеках.

## Baseline title and Purpose to restore after archive

Проба 2026-09-30 на копії репо (OpenSpec 1.13.2, дельта — повний текст базової спеки, де `## Requirements` замінено
на `## ADDED Requirements`): `archive` створює `openspec/specs/<capability>/spec.md` із заголовком
`# <назва каталогу> Specification`, переносить `## Purpose` без порожнього рядка після заголовка розділу, вимоги
лишає дослівно, а розділ `## Поза обсягом` відкидає. Дельта без `## Purpose` лишила б ще й заглушку
`TBD - created by archiving change add-input. Update Purpose after archive.`, на якій
`openspec validate --all --strict` падає (та сама проба). Тому дельти несуть повний текст, а тут лежать дослівні копії
трьох частин кожної базової спеки.

Відновлення (tasks.md, 5.10): рядок 1 замінити заголовком; розділ `## Purpose` зробити таким, як блок нижче (з
порожнім рядком після заголовка розділу); у кінець файлу дописати порожній рядок і блок «Поза обсягом». Готово, коли
`git diff cf8cdd9 -- openspec/specs/registry/spec.md openspec/specs/live-capture/spec.md` нічого не друкує.

### registry

Заголовок (рядок 1):

```markdown
# Registry Specification
```

`## Purpose` (до порожнього рядка перед `## Requirements`):

```markdown
## Purpose

Реєстр — TOML-файл, який веде людина: цільова бібліотека `lib`, команда перевірки `verify_cmd`, базова адреса
біржі `base_url` у секції `[live]` і список уже реалізованих методів `[[method]]` (FR-1–FR-10). Інструмент
перевіряє реєстр цілком до першого методу і на ваду відповідає кодом `2` з повідомленням, що називає винуватця
(NFR-11). Перевіряє він лише те, що називають FR-2 і FR-4–FR-10; решту значень реєстр, як v1, передає прогону
як є.

Умовності сценаріїв: «придатний реєстр» — реєстр зі сценарію «Базовий придатний реєстр приймається», а «варіант
придатного реєстру» — він же, де змінено лише названий рядок чи секцію; його `base_url` лежить у домені
`.invalid`, який не резолвиться. «Інструмент читає реєстр» — спостерігається лише прочитаний реєстр, який прогін
отримує до першого методу; «інструмент запускається» — процес CLI, від якого чекають коду `2` до першого методу;
«повідомлення містить `X`» — його stderr містить підрядок `X`.
```

«Поза обсягом» (кінець файлу):

```markdown
## Поза обсягом

Щоб тестувальник не приймав обсяг за дефект:

- Перевірки значень, якої немає і у v1: схеми й символів `base_url` і `path`, значень `args`, придатності slug.
  Погана адреса дає код `3` (див. capability `live-capture`, FR-26), значення без літерала Java — стадію `javac`
  (див. capability `field-verification`, FR-33).
- Виведення `model` і `client_method` для короткої форми (FR-11).
- Обробка дублів (FR-12, TC-19) і неоднозначних методів (FR-13).
- Звіряння `args` з документацією біржі (FR-95–FR-99, TC-11).
- `credentials` для підписаних ендпоінтів (FR-105, TC-14).
- WebSocket, розклад, інші біржі й бібліотеки (FR-106–FR-108, TC-15–TC-17); спільний DTO (FR-109, TC-21);
  реалізація методу з нуля (FR-94, TC-10).
```

Можливість `live-capture` для кожного методу, що пройшов ранні перевірки (FR-20–FR-22, див. capability `run-cli`),
робить одну спробу живого HTTP GET без ключів біржі і зберігає відповідь фікстурою `runs/<slug>/fixture.json`, бо
склад полів і значення енамів виводяться лише з живої відповіді цього прогону (принцип II). Якщо спроба не вдалася,
метод зупиняється з кодом `3` до перевірки і до будь-якої дії з бібліотекою, а повідомлення називає URL і причину.
Спека покриває FR-23–FR-30, NFR-4 і NFR-11 для повідомлень із кодом `3`; лише stdlib — див. capability `run-cli`,
NFR-14. Якщо не сказано іншого, `base_url` — `https://fapi.binance.com`.
